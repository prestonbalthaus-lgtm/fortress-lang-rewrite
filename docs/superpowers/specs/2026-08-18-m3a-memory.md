# Fortress M3a: the collector

Date: 2026-08-18
Status: implemented, gated

M1 shipped a leak on purpose. Every string returning shim allocated and nothing
ever freed, and the note in `shims.c` said so. The bet was that centralising
every allocation behind one function would make replacing it a change to one
function rather than a hunt through generated code. That bet paid: the
allocator swap is four lines.

M3a cashes it in before arrays arrive, because arrays are where allocation
stops being incidental.

## Boehm, not ARC

Both were on the table. ARC needs codegen to place retain and release calls,
which needs lifetime analysis across phis, returns and function arguments, and
getting it wrong produces a use-after-free rather than a leak. That is a
milestone, not a step inside one. Boehm-Demers-Weiser is thirty years old,
conservative, and known to work under exactly this pattern: a compiler that
emits ordinary C calls and lets the collector scan the stack and registers.

`02-stack.md` sanctions either. The order the work is in decided it.

## What changed in the runtime

```c
#define FORTRESS_RAW_ALLOC(bytes) GC_malloc_atomic(bytes)
void fortress_runtime_init(void) { GC_INIT(); }
```

Two details that are not incidental.

**`GC_malloc_atomic`, not `GC_malloc`.** Atomic memory is not scanned for
pointers. Strings are bytes, so scanning them is not just wasted work: across
two million allocations, a pair of characters that happens to look like a heap
address would falsely retain whatever it points at. Atomic allocation makes
that impossible.

This is a landmine for M3b and it is written into `shims.c` as a comment.
Arrays hold pointers. An array allocated atomically would have its contents
collected out from under it while it was still holding them. Arrays need a
scannable allocator built on `GC_malloc`, and the day that lands, this
distinction has to be understood rather than rediscovered.

**`fortress_runtime_init` is called from generated `main`, first.** A
constructor attribute would also run before `main`, but the collector has to be
up before the first allocation and `main` is the only place guaranteed to run
before anything else the compiler emitted. It is also the hook the next runtime
thing to need starting will use. On Linux `GC_INIT` finds the stack bottom from
`__libc_stack_end` rather than from its caller's frame, so being one call deep
is safe, and every Fortress value lives deeper than `main` regardless.

Boehm becomes a link dependency of every Fortress binary, the same way an MPI
program depends on `libmpi`. `runtime/shims.c` is compiled at link time by
whatever C compiler is linking, so `gc.h` is needed wherever a Fortress program
is linked: the build host, and the Apptainer image, which now carries
`gc gc-devel`.

`setup-gc.sh` handles the host without root, the same way `setup-llvm.sh`
handles LLVM. It unpacks `gc-devel` into `~/.local` and repoints its `libgc.so`
symlink at the installed runtime library, which is in the `gc` package and so
dangles when the devel package is unpacked alone. It restricts the download to
the distribution repositories, because a third party repo that wants a GPG key
imported will otherwise stop and wait for an answer.

## Proving it, with no loops in the language

Fortress has no `for` yet: iteration is M3b. A million iterations still has to
come from somewhere, and recursion a million deep is not it, both because the
stack will not take it and because every frame would hold its string live,
which is the opposite of what needs measuring.

Nesting solves it. `inner(1000)` recurses a thousand deep and unwinds
completely. `outer(1000)` calls `inner(1000)` and then recurses. Peak stack is
two thousand frames, about 200 KB, and the total is a million iterations at two
allocations each. Every string `inner` made is unreachable the moment `inner`
returns, which is exactly the condition a collector is supposed to exploit.

`gcsoak.fss` is that program at a million iterations. `gcsoak_lite.fss` is the
same program at ten thousand.

## The measurement

`tools/memory-gate.sh`, 17 checks.

The claim is scale invariance rather than a threshold someone picked. If memory
is collected, a hundred times the allocations costs the same resident set. If
it is not, it costs a hundred times as much. Measured:

```
   10,000 iterations, collected : 5,768 KB
1,000,000 iterations, collected : 5,760 KB
1,000,000 iterations, leaking   : 64,076 KB
```

A hundredfold workload, and the resident set did not move; the difference is
under a page and the wrong way round. The same program linked against M1's
allocator costs 11.1 times as much.

**The negative control is the reason the flat number means anything.**
`-DFORTRESS_NO_GC` keeps M1's `malloc` in `shims.c` and nothing in the compiler
ever defines it. The gate links the *same object file* against it, so the two
builds are the same program doing the same work, differing in one function.
Without that control, flatness would also pass on a workload too small to leak
visibly, and the gate asserts the control leaks by at least 5x for exactly that
reason.

**Both assertions are self tested before every run**, on real numbers from a
passing run: flatness must accept 5764 against 5760 and refuse 64080 against
5760, and the control check must accept 64080 against 5764 and refuse 5764
against itself. An assertion that always returns true and one that always
returns false both fail that.

**The mutation was run.** `GC_malloc_atomic` swapped back to `malloc` in the
collected path: 12/3, exit 1, caught three independent ways. The symbol check
saw `GC_malloc_atomic` gone from the undefined list, flatness measured 5,772 KB
growing to 65,256 KB, and the control check reported that the control no longer
distinguished anything from the subject.

`peak-rss.py` uses `os.wait4`, which reports rusage for one child.
`getrusage(RUSAGE_CHILDREN)` reports the maximum over every child the caller has
ever reaped, so a second measurement in the same process silently returns the
first one's number. That was caught by measuring three binaries and getting two
identical answers.

## --target-cpu

Separate from memory, and the blocker M2a recorded. `write_object` built the
target machine from `get_host_cpu_name`, so an object was built for whatever
machine ran the compiler.

`--target-cpu` now chooses, defaulting to `x86-64-v3`: AVX2 era, and every part
worth scheduling on has it. `skylake-avx512` is the Platinum 8160. `native` is
still available and is now opt in, which is the right way round.

The module also carries a triple and a data layout, which it did not before,
and every function the module defines is stamped with a `"target-cpu"`
attribute, so an object records what it was built for instead of leaving it to
whoever reads it.

The name is checked against a list before it reaches LLVM, because LLVM answers
an unrecognised processor with a warning on stderr and then builds for the
baseline anyway. That is a wrong binary rather than a failed build, and a typo
in a batch script should not produce one.

## What M3a does not do

No arrays, no iteration, no traits. The order is arrays then traits, and
nothing of either is built here.

The collector is stop the world and single threaded, which is correct for one
MPI rank per process and will need revisiting when M3d brings real threads.
