# What is left to get the Fortress compiler to v1

**Target.** ROADMAP.md decision 4 (ROADMAP.md:227-236): v1 is the complete Fortress 1.0 specification minus syntax abstraction (decision 1). Sixteen features are named explicitly in scope: reduction variables, distributions, `ZZ64` indexing, non-`RR64` floats, bits and storage types, integers beyond `ZZ32`/`ZZ64`, dimensions and units, keyword arguments, where clauses, coercion, modifiers, radix numerals, the types that classify operator properties, `nat` constraint solving, static arguments (`nat` with minus, `int`, `bool`, `dimension`, `unit`), and Unicode names.

**Where it is, bluntly.** 291 of 1956 corpus files compile end to end. On the honest denominator — `triage.sh --real`, which drops 368 must-fail and known-broken paths — it is 234 of 1588. Of the 291, 38 are files the corpus marks as must-FAIL (27 `XXX`, 11 `SXX`), and a second, larger and better-grounded must-fail record in the repo says 45 files that the legacy implementation refused are accepted. The largest program that has ever compiled end to end is 1,670 bytes; the whole set that has ever compiled is 162 KB across 291 files. Four `Library/` implementation files compile and they total 85 lines of empty stubs, one of which is nine lines of licence header and three of code. No name has ever crossed a file boundary: imports parse and are discarded. Phase 3 has not started, phase 4 has no engine to extend, and phase 0's exit artifact does not exist and was cancelled as a side effect of a different decision without the ROADMAP ever being amended.

The distance to v1 is large, and most of it is not in the features. It is in five architecture decisions nobody has written down, a critical-path library bootstrap that has a sequencing constraint nobody recorded, and a class of silent-wrong-output defects sitting *inside* the number everything is planned against.

## Accounting rules used throughout

Three denominators are in play. Every number below carries one.

| Denominator | What it is | Compiling |
|---|---|---|
| **1956** | raw corpus file count | 291 |
| **1846** | conformance denominator after ROADMAP decision 1 cuts syntax abstraction (1956 − 110) | not computed |
| **1588** | `tools/triage.sh --real`: 1956 minus must-fail prefixes and known-broken paths | 234 |

The 1846 denominator is stated by decision 1 and is implemented in **no tool**. `triage.sh` has `--real` (1588) and raw (1956) and nothing else, and 91 `syntax_abstraction_tests` files are inside the 1588. Any conformance percentage quoted today is quoted against a denominator the instrument cannot produce.

**"100% done" never means every corpus file compiles.** Must-fail negative tests must stay refused *by name*, and gate floors sit one below the count on purpose (`tools/apply-gate.sh:39`, `COMPILE_FLOOR = 290` against 291).

**There is no api gate.** `grep -rn 'api.gate|api_gate'` over the repo returns nothing; `tools/` holds apply, array, atomic, dispatch, generics, memory, mpi, mpicc, operator, parallel, triage and unit gates plus `peak-rss.py`. "16 of 114 reach the api gate" is a hand count in `04-state.md` meaning: the file parsed, `Checker::new` registered its declarations, and the last diagnostic is `ApiNotExecutable`. Call it **the api terminus**. Scripted and reproduced today: **16 of 62** top-level `Library/*.fsi` + `CompilerLibrary/*.fsi` reach it. The "114" denominator matches nothing the repo defines — `Library/` is 126 files recursively and 104 at top level (decision 1 states 126 outright); the census composition is most consistent with Library top-level 104 + CompilerLibrary 10, unverified. Label it *the census set*, never `Library/`.

**Sizing.** Exactly two forms appear below: `measured: X (who, when, against what baseline)` or `needs a spike: NAME`. No effort estimate appears that no spike produced. This is not conservatism — `docs/superpowers/specs/2026-08-19-m3h-getters-self-values-design.md:17-30` re-measured the ROADMAP M3f construct table on a later tree, published a three-column stale-vs-remeasured table in which *every construct measured higher than its estimate*, and closed with **"Re-spike before every milestone. Do not carry a number forward."** Six milestones have landed since M3f. Every price from that table (getter/setter, `var`, `opr`, top-level values, object expressions, enclosing operators) is therefore absent from this document. The same source records that construct payoffs are **superadditive**: getter + `self` + top-level values measured +138 together against +124 as parts. A solo-spike price is a floor for the bundle it belongs to and a ceiling for nothing.

**The histogram lies.** First-blocker counting has been wrong five milestones running: the traits marker ceiling said 202 files, a spike delivered 10; the `opr` `alone` column said 9, the spike delivered 5. Plan from `alone`; `alone` **orders**, it does not **price**. And 279 failing files (221 under `--real`) carry no marked feature at all, so the triage table is structurally blind to part of what it is measuring.

**Verification.** Every figure attributed to "verified today" was reproduced against master `f81f41ace` on 2026-08-21 from the existing `fortressc/build/triage.json` cache or by running the shipped debug driver. No corpus re-sweep was performed.

### Phase 0 — not met, and the ROADMAP was never amended

The exit is `legacy interpreter runs ProjectFortress/tests/ and the pass/fail set is recorded in the repo. That recorded set is the target, not the specification.` (ROADMAP.md:121-124). **No such recorded set exists anywhere in the tree.** `find . -iname '*baseline*'` returns nothing.

It was cancelled as a *side effect* of a different decision: `docs/superpowers/specs/2026-08-18-fortress-m1-design.md:16-19` — "The JVM is excluded from the toolchain and from the output. That decision also removes the legacy interpreter as a differential oracle, since it only runs on a JVM" — and its open items say "No differential oracle exists. Every expected output is verified by a human" (:226-229). The ROADMAP was not updated. Three live commitments still name the oracle: phase 4's exit ("disagreements with the legacy interpreter documented rather than silently matched"), phase 5's exit ("produces the same output as the interpreter"), and the deletion trigger at ROADMAP.md:259-260 ("stays only as a differential oracle and gets deleted once phase 7 passes") — which would destroy the only thing that could produce the missing baseline.

Toolchain state on this machine: `java` is OpenJDK 25.0.4; `javac` and `ant` are not installed. The legacy tree is Java-6-era Ant code. `03-guidelines.md`'s `<forbidden>` explicitly *exempts* building the legacy implementation for study, so policy is not the blocker — tooling and a decision are.

**The substitute is already in the tree and nobody knew.** 373 `.test` files (verified today) carry the legacy implementation's recorded expectations, driven by `ProjectFortress/src/com/sun/fortress/tests/unit_tests/FileTests.java:141-186`. Census: `compile` 332, `compile_err_equals` 264, `run` 97, `link` 96, `run_out_equals` 38, `run_out_contains` 33, `run_out_does_not_contain` 19, `run_out_WIcontains` 8, `run_out_matches` 8; 92 carry at least one `run_out_*`. 43 name more than one component (they need separate compilation, i.e. phase 3); 2 carry `arg1=` (they need varargs). Reading them requires no JVM — only writing them did, and that was done twenty years ago. Nine area reports, nine verdicts, ROADMAP, `04-state.md`, `SYNTAX_GUIDE.md` and every script in `tools/` contain zero references to them.

### Phase 1 — met

Lexer floor is 1780 of 1956, asserted as a ratchet at `fortressc/crates/lexer/tests/corpus.rs:130-131`. No panics observed anywhere: across roughly 400 probes run by nine independent mappers plus their verifiers — including deliberately hostile input (unterminated comments, bad escapes, control characters, four-bar operator runs, 25-digit literals, multi-gigabyte allocations, a 10^9-iteration parallel loop) — every failure was exit 1 with a diagnostic. Zero exit 70, zero exit 101. The M1 fail-fast design holds.

### Phase 2 — partially met, and the published status is stale by 4x

Parser floor is **637 of 1956 (33%)**, asserted at `fortressc/crates/parser/tests/corpus.rs:144-145`. The exit demands 90%. ROADMAP.md:135-137's own status line reads "1780 of 1956 lex (91%), 168 of those parse" — that number is stale by nearly a factor of four and is the kind of figure a reader takes as current.

### Phase 3 — not started

The exit is `Library/ resolves clean with no unresolved references`. Nothing resolves against anything. `import Foo.{...} except {...}` parses; `ImportDecl` carries only `{api_name, is_api}`; the brace group and the `except` clause are consumed by `skip_braces` as balanced token runs and discarded. `Component.imports` has exactly one reader in the whole workspace — `mono.rs:421`, which clones it. `Component.exports` has two clone sites and no readers. An import of a nonexistent api naming nonexistent members with a nonexistent exclusion compiles clean; `export NotAnApiAtAll` compiles and links. There is no source path, no api-name-to-file map, no cache, no repository (`default_repository/` contains one file and it is the *legacy* implementation's property file). The driver accepts exactly one positional source and a second one silently overwrites the first.

115 of the 1588 `--real` files first-block on `missing-library` names that only an import could supply.

### Phase 4 — not started as specified, and the specification of it is wrong

`02-stack.md` and ROADMAP phase 4 both describe a Hindley-Milner engine. **There is none.** `grep` for `unify`, `TypeVar`, `Substitution`, `occurs_check`, `fresh_var` across `fortressc/crates` returns zero hits; `Type` (`crates/types/src/types.rs:86-102`) has no variable case. What exists is bidirectional checking against `expected: Option<Type>` (33 sites in `types/src/lib.rs`) plus one declaration-order fixpoint over inferred *return* types. The difference between "phase 4 extends an engine" and "phase 4 builds one" is the whole cost of the phase.

The split decision 4 itself demands ("Phase 4 is no longer one phase... Split phase 4 before starting it and give each part its own exit criterion") has never been written.

And the exit criterion is **unreachable as written**: `Library/QuickSort.fsi` declares `quicksort[\T\](...)` alongside `quicksort[\T extends StandardTotalOrder[\T\]\](arr:Array[\T,ZZ32\])`. `Specification/basic/overloading.tex:100-105` forbids that verbatim, the compiler correctly refuses it, and so "type checks `Library/`" cannot be satisfied while enforcing a rule 1.0 states and 1.0's own shipped library breaks. That needs a signed-off deviation of the M3c kind, not a fix.

### Phase 5 — the compile half only

`tools/apply-gate.sh:202` runs the corpus sweep as `[fortressc, p, '--emit-obj', '-o', '/dev/null']`. It never links and never runs. `triage.sh` uses the same invocation. So **"291 compile" means "exited 0 while emitting an object"**, and nothing anywhere checks what any of the 291 prints. Every gate that *does* run a binary runs fixtures under `fortressc/tests/` (73 files), never a corpus file, and its oracle is a hand-written expected string in `crates/driver/tests/end_to_end.rs` — the "verified by a human" oracle the M1 design named.

Two new measurements close part of this gap:

- **All 291 compiled to binaries and executed** (20s timeout, `FORTRESS_WORKERS=2`): 288 exit 0, 0 timeouts, **3 die with SIGSEGV** — `ProjectFortress/long_term_not_working/overriding/{Diamond,Graph,RedundantGraph}OverridingParams.fss`. Cause is unbounded mutual recursion through overridden methods (`m(z:String,t:String) = m()` and `m() = self.m("a","b")`), so it is a stack overflow with no stack guard — a fault with no diagnostic, in a project whose stated rule is that a subscript "halts with a diagnostic and exit 1 rather than faulting". Whether 1.0's overriding rules made that recursion finite is exactly the question an oracle would settle, and the `.test` set has no case for those three files.
- **The `.test` runtime expectations were run against the rewrite for the first time.** 16 cases have every named source compiling today; all 16 built and ran; all 15 that carry an implementable assertion **pass**, including four exact whole-stdout `run_out_equals` matches (Compiled10, Compiled13, Compiled15, Compiled70, EmptyDoEnd, ForLoops, ParametricFields, SingleInheritanceNotUsed). The 16th uses `run_out_WIcontains`, which the throwaway runner did not implement, so it asserted nothing — do not count it. This is the only externally-sourced evidence of runtime correctness this project has, and it is good.

### Phase 6 — the C-ABI half is done and gated

A Fortress program links against a real OpenMPI inside `apptainer/fortress-mpi.sif` and runs as four ranks; `tools/mpi-gate.sh` covers it. What remains of the exit is the literal *two-node* rank count and there is no cluster. Note also that the boundary is four arity-zero shims: `MpiOp` is exactly `{Init, CommRank, CommSize, Finalize}`, and there is no point-to-point or collective operation of any kind. Separately, there is **no declaration form by which user Fortress source can name any other C function** — `native` is parsed, carried on `Modifiers`, copied through `mono.rs`, and read by nothing, so a Fortress program cannot call BLAS or libm without a compiler change.

### Phase 7 — met, measured for the first time, and asserted by nothing

Both halves pass on the shipped compiler:

| Workload | Sequential | Parallel | Speedup |
|---|---|---|---|
| `for i <- 0#10^9 do total += i i end` (range) | 0.82–0.88 s (`seq(...)`) | 0.09–0.11 s at 14 workers | **9.1x** |
| 10^9-element `Array[\ZZ32\]` fill + sum | 5.07 s (`seq(...)` both loops) | 1.92 s at 14 workers | **2.6x** |

The range answer is `3338615082255021824` and it matches the closed form `(n-1)n(2n-1)/6 mod 2^64` — verified against arithmetic, not merely self-consistent — and is identical at 1, 2, 4, 8 and 14 workers. `ZZ64` indexing past 2^31: a 3,000,000,000-element `Array[\Boolean\]` written and read at index 2,999,999,999, exit 0, 1.08 s, 2.9 GB RSS; and the truncation discriminator halts correctly (`fortress: array index out of bounds (4294967296, 4)`) rather than wrapping.

Three things follow. (1) The array reading is **bandwidth-bound**, so a gate floor written against it must be 2.6x, not the range form's 9x — and it must be referenced to a true `seq(...)` build, not to parallel-with-one-worker. (2) Nothing in the repository asserts any of this: the largest reduction fixture is `fortressc/tests/reductionbig.fss` at 20,000,000 iterations, 50x short, and `grep` over `tools/` for `1000000000` or `2147483` returns two comment lines in `crates/types/src/lib.rs`. (3) **Every performance number in this project, including these, is an `-O0` number** — see §6.

### Phase 8 — shelved by standing decision

ROADMAP.md:16-19 and `02-stack.md`'s 2026-08-18 posture: "There is no cluster to test on, and MPI is not what is blocking the language." Phase 7's exit says "on one node", so the shelving does not touch it.

## 2. The critical path: the library bootstrap

Phase 3's exit is the gate on everything measurable. This section is the dependency order.

### 2.0 Two structural facts nobody wrote down

**API-first is architectural, not a preference.** Over the `.fsi` files the api dependency graph is **acyclic in 5 layers over 57 nodes** (32 / 12 / 7 / 4 / 2). Over the `.fss` files the same computation strands **File, FlatString, FortressLibrary, Reader, Stream, String and Writer in one 7-file mutual cycle**. `Specification/basic/components/overview.tex:26-33` says why: components never refer to other components directly; all external references are to apis. **An api resolver is a strict prerequisite for a component resolver.** Any phase-3 plan that starts from `.fss` files deadlocks immediately.

**Source-path order is load-bearing input, not a convenience.** Ten api names exist in more than one directory — Executable, File, FileSupport, FlatString, FortressLibrary, List, Map, Pairs, Set in both `Library/` and `CompilerLibrary/`, and System in all three. They are *different libraries*, not copies: `ProjectFortress/LibraryBuiltin/System.fsi` reaches the api terminus while `Library/System.fsi` and `CompilerLibrary/System.fsi` both die on `unknown type ImmutableArray`. The legacy answer is on disk and reusable verbatim — `default_repository/configuration:44`: `.;${_fr}/LibraryBuiltin;${FORTRESS_AUTOHOME}/Library;${_fr}/test_library`. This also means the **bootstrap set is not the census set**: `FortressLibrary.fss:13-14` imports `NativeArray` and `NatReflect`, which live under `ProjectFortress/LibraryBuiltin/`.

Layer-0 apis that reach the api terminus today (12 of 32 by name, resolving `System` to the LibraryBuiltin file under the legacy path order): AnyType, CompilerAlgebra, Executable, Heap, Lazy, OneShotFlag, StatDigest, System, Testable, Timing, Treap, TypeProxy. Layer 1 adds Generator2 and Shuffle; layer 2 Reader and SetClosure; layer 3 Relation. **`FortressLibrary` itself sits at layer 2**, so "the root everything imports" has two answers: `FortressBuiltin` is the unconditional one (layer 0, `Specification/library/default-libraries.tex:12-38`), `FortressLibrary` the default-imported one.

### 2.1 Step 0 — re-base the instruments before planning anything off them

This is measurement, not feature work, and it comes first because two confirmed mechanisms inflate the number every plan is steered by.

**(a) Script the api census.** It is a hand count today. For each file in the census set: exit 0 = compiles; last diagnostic `an \`api\` is a set of signatures with no bodies` = api terminus; anything else = blocked, bucketed by diagnostic. Emit the per-file list, not a count. Settle the 114-vs-126 denominator in the same commit.

**(b) `SPIKE-TEMPLATE-WELLFORMEDNESS` — find out how much of the count is not real.** Three independent inflation paths, all probe-confirmed:

- An **uninstantiated generic body is never checked**. `f[\T\](x: T): ZZ32 = "not a ZZ32" + nosuchname` with no call site → exit 0, links, runs. Add one call → exit 1.
- A **generic declaration header naming a type that exists nowhere resolves to nothing**. `trait R[\T\] extends Nowhere[\T\] end` → exit 0; the non-generic `trait R extends Nowhere end` → exit 1, `unknown type \`Nowhere\``.
- An **override is only checked at a dispatch site**. A trait method returning `ZZ32` overridden by an object method returning `String` links and runs if nothing calls it through the trait.

This is not theoretical for the headline library number: **`Library/Relation.fsi` is inside the 16 while declaring `extends ContainmentBySubset[\Relation[\T\]\]` from an unresolved import**, and `Library/Reader.fsi` is inside the 16 only because its `extends ReadStream` is commented out at line 17. Landing real import resolution will make some of the 16 go **red**, not green.

*Spike:* check each generic template once at fresh opaque type parameters before expansion, and resolve declaration-header type names at registration time even when nothing instantiates. Re-run the full 1956 sweep and the api census. Report how many of the 291 and how many of the 16 stop passing.
*Branch:* small drop → every baseline below survives on today's numbers. Large drop → re-base before scheduling anything.

**(c) Patch the triage source-marker table.** `tools/triage.sh:235`'s `aggregate-literals` marker regex is `<\||\|>|\{\s*\w` — it **never matches a bare `||`**. The largest single first-blocker feature in the corpus has no `alone` ceiling recorded anywhere in the instrument the project says to plan from. The table also has no row for tuples, radix numerals, character literals or library builtins, and its `control-flow-extras` row misses four `spawn` files. Grouping the 221 unmarked `--real` failures by final diagnostic shows they are not a hidden feature — the top is `expected \`)\`, found BarBar` 11, `expected \`)\`, found Colon` 10, `a tuple expression is not implemented` 9, `expected an expression, found Bar` 9, `expected \`:\`, found RParen` 8 — every one of which is a feature already mapped. What is missing is marker rows. One `sed` and a `--reuse` re-run, **before** the operator spike is designed.

### 2.2 Step 1 — `SPIKE-VARARGS`, and the parser-local defects that ride with it

**Why first.** It blocks the bootstrap root. `Library/FortressLibrary.fsi` dies at byte 8254, line 234, on `assert(x:Any, y:Any, failMsg: Any...): ()` — reproduced on master today, and `04-state`'s own trail 329 → 74 → 234 confirms it has not moved. It also blocks the spec's own `Executable` api, `run(args:String...):()` (`Specification/basic/components/basic.tex:178-184`), which **1526 corpus files of 1956 export** — so the component-satisfies-api work in step 5 cannot run before it. And `Specification/basic/expressions/aggregate.tex:44-47` defines set/map/list aggregates as calls to a bracketing operator **with a varargs parameter**, so it is a prerequisite of the largest first-blocker bucket in the corpus, not a sibling of it.

**Mechanism.** There is no `...` token — it is three glued `Dot`s, and `params()` stops at the first. Also needed: the enclosing-operator form `opr <|[\E\] xs: E... |>` (static parameters *between* the opener and a vararg operand), which List, PureList, Set, Map, IntMap and CompilerLibrary/List all declare.

**The question the spike must answer before any count means anything.** What does `Any...` lower to. `Specification/basic/functions.tex:174-182` says `HeapSequence[\T\]`, a library type that does not exist. The compiler has only `Array[\T\]`, and `fortress_array_alloc` **refuses a reference element type by design** — the allowlist exists because a pointer slot pre-filled with a one-byte `""` would hand dispatch a tag load four bytes into a one-byte object (`02-stack.md`, Arrays). Stub the callee side (accept and ignore) *first* and report how many census files move from a `Dot` diagnostic to a **later** one, before committing to a representation.

**Ride-along, all parser-local, all blocking census files:**
- **Named `end Id`** (`end StringStats`, `end DefaultGeneratorImplementation`, `end Object`) — blocks `Library/String.fsi`, `Library/GeneratorLibrary.fsi` and `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi`, the file that declares `Object`. 13 corpus files.
- **Continuation-line declaration headers.** M6 fixed `extends`/`comprises`; a *function* header whose static-parameter list continues onto the next line still dies (`Library/RangeInternals.fsi:576` → `expected \`(\`, found Newline`), as do `CovariantCollection.fsi` and `ReflectiveQuickCheck.fsi`. A `where` clause on a continuation line also still dies, with a diagnostic naming the wrong mechanism (`expected a field or method name, found KwWhere` — a where clause is not a member). *Note the scope honestly:* only 15 of 1956 corpus files write `where {` at all, 8 of them on a continuation line, and **zero** are first-blocked on it inside `--real`. It is a correctness and diagnostic fix, not a library wall.
- **The `=`-followed-by-operator-character guard.** `raw.rs:282-290` hoisted a *binding-position* rule (`equals = "=" (!op)`, referenced in the legacy grammar only from binding and keyword-argument positions) into the **lexer**, where it applies to every `=` in the file. Three of its four casualties are census files: `Library/QuickCheck.fsi`, `Library/QuickCheck.fss` (`opr ==>`) and `Library/RangeInternals.fss:453` (`ex=-1`).

*Branch:* re-census immediately. The 329 → 74 → 234 precedent says expect a new wall behind this one; do not commit to step 2's scope until the post-varargs census is in hand.

### 2.3 Step 2 — `SPIKE-OPEXPR`, the operator expression grammar, widened

`04-state` already names this as the next spike. It is the right head and it is under-scoped in four ways.

**It is the top of two independent measurements.** The census puts infix `||` at 4 census files, named infix (`a SUBSET b`) at 6, the enclosing-operator-with-statics form at 5. And decomposing the 154-file `aggregate-literals` bucket (143 under `--real`, the #1 bucket) by the actual offending token gives: **60 files on infix `||`**, 37 on enclosing-bar application, 26 on `<|...|>`, 20 on `{...}`, 9 on `export { }` (which is imports, not aggregates), 2 on `RightBar`. The largest single first-blocker **feature** in the corpus is infix `||`, and it is filed under aggregate literals.

**Lexical prerequisites the spike cannot name its own operators without.**
- Six ASCII ordinary operator characters — `!` `?` `~` `$` `%` `@` — produce **no token at all**, only the default `UnrecognizedCharacter`. Real declaration sites: `Library/incomplete/basic/Fortress.Number.fsi:136` `opr (self)! : NN`, `ProjectFortress/BirdyLib/Bazaar.fsi:22` `opr BIG $()`, `SpecData/examples/advanced/OprDecl.Nofix.fss:23` `opr @()`. 40 corpus files first-block on the message.
- A run of **three or more vertical lines** splits into `BarBar` + `Bar`, where `Specification/basic/lexical-structure.tex:1174-1177` makes any run of two-or-more one base operator. `opr |||` is declared at `Library/FortressLibrary.fsi:1991` and `:2349-2350`. It survives in *declaration* position only because the parser re-glues adjacent `Bar`s by span adjacency — `opr |||(...)` emits `define i32 @"|||"` — so the failure is expression-position only. **That asymmetry is what the spike needs to know: the fix's risk sits in the parser's existing adjacency reading, not in the regex.**
- `^T` and the general superscripted-postfix rule. `Symbol.rats:199` has an explicit `caret = "^" !("T")` guard that was dropped, so `3^T` becomes two tokens and reports `unknown name \`T\`` — a wrong-token case, not a refusal. The wider rule (`Specification/basic/lexical-structure.tex:1204-1218`, any simple operator immediately preceded by `^`) is absent, and `not_passing_yet/HatOps.fss:19-24` writes `A^*`, `A^TH`, `A^TT`.

**Named infix is a LEXICAL rule, not a declared-operator table.** `Specification/basic/operators/operator-app.tex:28-33`: a token of uppercase letters and underscores, not beginning or ending with `_`, containing **at least two different letters**, is an operator — MAX and MIN are the worked examples. The "two different letters" clause is what keeps `ZZ`/`RR`/`QQ` identifiers; digits keep `ZZ32`/`RR64`; `BIG` is already reserved. And `opr-fixity.tex:28-32` makes the decision binding: "The Fortress language dictates only the rules of syntax; whether an operator has a meaning when used in a particular way depends only on whether there is a definition in the program." So `a SUBSET b` must **parse** as an infix application whether or not any `opr SUBSET` exists, and only then fail to resolve. Driving the syntax off `opr` declarations inverts that.

**The real risk is retroactive, and measuring it is the spike's job.** Implementing the lexical rule invalidates every all-caps binding in the currently-compiling set. `SUBSET: ZZ64 = 2` binds cleanly today and should not — which is also why `println(3 SUBSET 4)` prints **24** (see §6).

**`fixity_at` is not the machinery two proposed spikes assumed.** `parser/src/lib.rs:231-238` is `match (glued_left, glued_right)` — adjacency only, four arms, no context term, and its own doc comment says "from adjacency alone". `Specification/basic/operators/opr-fixity.tex:34-55` is a **twelve-row left-context/right-context table** in which whitespace is a secondary discriminator on only some rows. Adjacency alone cannot decide `|` in `a |b| c`. Any encloser or named-infix work resting on `fixity_at` rests on the wrong thing — and the mis-modelling is not hypothetical, it is the direct cause of the fixity inversion in §6.

**Decide precedence WITH it, not after it.** `Specification/basic/operators/precedence.tex:20-31` makes Fortress precedence a **partial** relation: "If there is no specific precedence relationship between two operators, then parentheses must be used" — `a + b CUP c` must be **refused**. The parser is a fixed total ladder that can only ever accept. Adding a second operator family into a total ladder makes wrong grouping *silent*, which is the worst class this project recognises. Encode the `precedence.tex:104-138` shape groups as a partial order in the same change, and prove it by showing `a + b CUP c` refuses.

*Branch:* step 0(c) gives infix `||` an `alone` ceiling first. If it is large, do the `||` half and re-measure. If it is small (the bucket's current `alone` is **2**), the 60 is a wall other work hides behind and the `||` + encloser + varargs + generalized-`if` cluster has to land together to move anything — which is exactly what the GenomeUtil evidence in §4 shows.

*Unlocked only here:* `||=` and the six operator-word compound forms; `a SUBSET b` in 6 census files; conditional operators `AND:`/`OR:` (fold in, do not spike separately); superscripted postfix; multifix (an arity filter over M3c's existing overload sets once a table exists).

### 2.4 Step 3 — the Unicode allowlist (decision 3's lexer half)

Decision 3 settled the *shape* — ASCII core, Unicode as a curated allowlist plus library aliasing, explicitly not Sun's `ID_Start`/`ID_Continue` dump — and the allowlist itself does not exist. Every non-ASCII byte outside a comment or string is a hard lex error.

**Measured scope, and it is small and exact.** Across all 136 `Library/` + `CompilerLibrary/` files with comments and strings stripped: **18 distinct non-ASCII codepoints across 6 files, and zero of them are letters.** Six alias tokens the lexer already emits — U+27E6/U+27E7 → `LGeneric`/`RGeneric`, U+21D2 → `FatArrow`, U+2264 → `Le`, U+2265 → `Ge`, U+2260 → `NotEq`. The other twelve (U+2229 INTERSECTION 16 uses, U+2190 12, U+2208 6, U+226B 6, U+2286 5, U+226A 5, U+2192 4, U+27E8/9 3 each, U+2287 2, U+00AC 1, U+2228 1) are operators that land nowhere until infix operator expressions parse.

**Therefore this follows step 2, not precedes it.** The table alone moves the six aliasing codepoints and stalls on the twelve.

**A wrinkle in decision 3's wording that nobody noticed.** It scopes the allowlist to "codepoints legal in identifiers and operators". U+27E6/U+27E7 are **brackets** (the Unicode spelling of `[\` and `\]`) and U+201C/U+201D are **string delimiters** — neither is an identifier or an operator, so decision 3's wording does not cover them and neither can be a library alias. Curly-quote string literals are a genuinely missing spec form (`lexical-structure.tex:290-297`, `Literal.rats:151-155`) with a **positive** corpus test, `ProjectFortress/tests/matchingStringMarks.fss`, whose must-fail twin `XXXNotMatchingStringMarks.fss` is correctly refused.

*Out of scope here:* arbitrary Unicode identifiers. The only four corpus files needing letter codepoints (Hangul, the full Hebrew alphabet) are exactly the files decision 3 declines to serve, and **no census file needs a single Unicode identifier character.**

### 2.5 Step 4 — `SPIKE-IMPORT-RESOLUTION`, the first thing in phase 3 that is phase 3

Three constraints the spike must respect, beyond the two structural facts in §2.0:

**Qualified names at use sites are in scope or the spike has no collision answer.** `Specification/basic/components/source-code.tex:280-287` disambiguates "the type `List` declared in the API `List` or the type `List` declared in the API `PureList`" with a qualified name, and the compiler cannot express one: `f(x: List.List)` → `expected \`)\`, found Dot`; `println(System.args)` → `unknown name \`System\``. With ten duplicated api names on the source path, collisions are not hypothetical. Qualified-type parse failures also land in the `imports-and-exports` bucket via `found Dot`, which is a fourth feature stapled into that bucket.

**The phase-order constraint inherited from M3d.** `registry.concrete` and every type tag **freeze at `Checker::new`**, and `mono::expand` runs to a fixpoint before it (`types/src/lib.rs:52-55`). Seeding imported names must happen before `Checker::new`, in the same pre-checker slot expansion occupies. This is the same generalisation the reverted `Object`/`Any` spike used.

**Ride-along:** dotted and braced export names. `parser/src/lib.rs:272-282` calls `identifier("an export name")` for the export while `:265` calls `dotted_name()` for the component header fourteen lines above — so `component Compiled5.a` parses and `export Compiled5.a` does not. 21 dotted + 9 braced first-blockers, plus the 9 `export { }` files mis-bucketed into aggregates.

Also here, and cheap: `import java <foreign>` is refused with a generic `expected a newline or \`;\`, found Ident("com")` rather than a diagnostic naming the construct. 39 corpus files, 37 of them legacy JVM test directories — but three are bootstrap files (`Library/CompilerSystem.fss`, `ProjectFortress/LibraryBuiltin/{CompilerBuiltin,System}.fss`) whose bodies reach the JVM this way and have no other implementation in the tree. **Those three bodies are C-shim work, not import work.** The only phase-3 obligation is a diagnostic that names the construct.

### 2.6 Step 5 — api check mode, then component-satisfies-api

**`SPIKE-API-CHECK-MODE`.** `Checker::run` refuses `is_api` as its **first statement** (`types/src/lib.rs:821-825`), before `discharge_bounds` and before any body is checked — so the message is a stub sitting exactly where phase 3 goes. Replace with a signatures-only path that runs `discharge_bounds`, resolves every declaration header, and exits 0. **Run this after step 0(b) or the two effects are indistinguishable.**

**Conformance.** `source-code.tex:313-320`: a component must satisfy every top-level declaration in any api it exports; `private` declarations do not participate; a trait's `extends` clause in the component must be *identical* to the exported api's. Today the driver takes one file, `exports` has no readers, and nothing compares a `.fss` to a `.fsi`. **Gated on varargs**, because the `Executable` api is `run(args:String...):()`.

**What becomes load-bearing the day this lands** — each currently inert and each cited as such in §5:
- `private`, which today restricts nothing (a private field is read from `run()` at exit 0).
- `comprises`, recorded and never read — `source-code.tex:290-299` makes a trait's exported hierarchy a fact about the api. Note this also closes the deliberate `comprises { ... }` open-set drop, because `comprises.tex` makes `...` legal only in an api.
- Component name versus file name, never compared (a file declaring `component TotallyDifferentName` compiles; `XXXcom.sun.test8.fss` is the pure must-fail case), and a **headerless file compiles with an empty component name that becomes the LLVM module id**.
- Duplicate `export`, duplicate import-on-demand, and an api both imported and exported — all three are static errors in `intro.tex:38-63` and `source-code.tex:301-303`, and all three compile at exit 0.

### 2.7 Step 6 — builtin seeding, and the decision hiding inside it

**`Object` and `Any` were spiked and reverted.** `04-state` records the chain: baseline 224 compile (must-fail dropped) → 227 with the parse wall removed → 234 with `Object`/`Any` seeded as root traits. **That number must be re-measured, not quoted.** The parse-wall half has since landed as `f81f41ace`, and `triage.sh --reuse --real` at master today reports **234 of 1588** *without any seeding* — the spike's endpoint and today's baseline are the same number for unrelated reasons. Whatever `Object`/`Any` is worth from today's baseline is unmeasured. It still ranks: `Object` and `Any` were 34 of the missing type names, they are the top of the 1.0 hierarchy everything hangs from, and they are a partial prerequisite for the trait join in §4 (without a top, a join over the lattice is partial by construction).

**The decision hiding in here, and it is not a seed.** `Registry::resolve` matches `ZZ32`/`ZZ64`/`RR64`/`Boolean`/`String` **by name before the trait and object tables**, so a builtin name can never resolve to a `Type::Trait`. `object MyStr extends {String}` → `` `String` is not a trait, so nothing can extend it `` — and `Library/FlatString.fsi` and `CompilerLibrary/FlatString.fsi`, both **layer-0 apis**, die on exactly that. Meanwhile `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:412` declares `trait ZZ32 extends { Number, Equality[\ZZ32\], StandardTotalOrder[\ZZ32\] } excludes { ZZ64, RR32, RR64 }` and `Library/FortressLibrary.fsi:461` declares `trait ZZ32 extends { ZZ64, Integral[\ZZ32\] }` — the two library declarations **contradict each other** (excludes `ZZ64` versus extends `ZZ64`) and both contradict the primitive.

An import resolver cannot seed these names blindly. And the registry comment blaming M3d ("a scalar implementing a trait would force boxing, which is M3d") is **stale** — M3d landed and chose monomorphization over boxing. Decide it before step 4 ships, because step 4 is what starts pulling those declarations into scope. Downstream: the numeric tower, the operator-property traits, coercion declarations (15 of the corpus's 48 `coerce` uses are CompilerBuiltin's numeric tower), and decision 4's "integers beyond ZZ32/ZZ64" and "non-RR64 floats", all of which need the tower extensible in the library rather than hardcoded in a nine-variant enum.

## 3. Architecture decisions still owed

Every item here gets more expensive the longer it waits, because each is a shape other work is currently being built around. Four are **decisions to write** and can be taken in parallel with §2. Four are **mechanism spikes** whose result picks a branch that then constrains months of work.

### 3.1 Decisions to write — no code

#### D5. The component algebra: separate compilation, in or out

**There is no recorded decision anywhere, and this is the sharpest governance finding in the whole review.**

`Specification/basic/components/` (10 `.tex`, 2011 lines) specifies a persistent component database with `compile` / `install` / `link` / `upgrade` / `extract` / `constrain` / `hide`, plus `advanced-lib/components.tex` (the reflective `Fortress.Components` api) and `appendices/components.tex` (the calculus). ROADMAP has decisions 1-4 and none touch it. Its "Out of scope for v1" section names Eclipse, Emacs, Fortify, Vim and `contrib/` and nothing else. A grep across `ROADMAP.md`, all `docs/superpowers/specs/*.md` and `tools/*.sh` for separate-compilation language returns **exactly one hit, and it is a postponement**: `2026-08-18-m3c-dispatch-design.md:26`, "The 1.0 rules come back the day `api` and separate compilation".

**Why it is urgent: two landed decisions structurally assume it never arrives.** M3c dispatch is **closed-world** — every tuple of concrete types is enumerated whole-program, and that one computation is the ambiguity check, the dispatch table *and* the exhaustiveness proof. M3d is **whole-program monomorphization** with `registry.concrete` frozen at `Checker::new`. Either D5 cuts the component algebra, or M3c and M3d re-open. Every additional milestone built on closed-world raises the cost of re-opening.

Decision 4 says v1 is the complete 1.0 spec minus syntax abstraction, which **literally includes this chapter**. Phase 3's exit criterion requires none of it. The two readings disagree and neither is written down.

**Already true in the backend either way:** every emitted object contains `main` unconditionally (a pure library component compiled with `--emit-obj` shows `T helper` *and* `T main`), and user functions are emitted as bare unmangled globals. Two `fortressc` objects cannot be linked at all. Whatever D5 says, symbol mangling and entry-point selection are a prerequisite of any two-file story.

#### D6. The phase-4 split that decision 4 itself demands

Decision 4: "Dimensions and units, coercion, where clauses and `nat` constraint solving are four separate inference problems that happen to live in the same checker, and unit algebra in particular has to survive inference rather than being checked after it. Split phase 4 before starting it and give each part its own exit criterion." **The split has never been written.**

Two things the split must state that nobody has:

1. **The four are not independent, and the where clause is what couples them.** `Specification/basic/trait-parameters.tex:294-301` lists the where-clause forms: trait constraint, type alias, `NatConstraint`, `IntConstraint`, `BoolConstraint`, `UnitConstraint`, `T coerces U`, `T widens U`. Nat solving, unit equality *and* coercion all arrive through where-clause syntax. Sequencing them as four parallel workstreams builds the same substrate three times; the where-clause representation has to land first. (Caveat for whoever writes it: `trait-parameters.tex:286` carries the spec's own `\note{The where clause syntax in this section is out of date.}` directly above that grammar.)
2. **There is no HM engine to extend** (§1, phase 4). "Builds one" and "extends one" are different phases.

A third item belongs in the same document: **the `Library/QuickSort.fsi` deviation**, because the phase-4 exit criterion is otherwise unreachable (§1).

#### D7. Reconcile `nat` — `02-stack` "permanent" against decision 4 "v1"

`02-stack.md` lists `` `nat`/`int`/`bool`/`opr`/`unit`/`dim` refused at the parser `` under **"Locked constraints"**, which in that file means permanent. Decision 4 lists `nat` constraint solving *and* static arguments (`nat` with minus, `int`, `bool`, `dimension`, `unit`) as **v1**. Both are current. The parser refusal is real, with a named diagnostic per kind (`` `nat` static parameters are not implemented; M3d is type parameters only ``).

**Why it is a decision and not a spike.** `trait-parameters.tex:81-82` says nat/int/bool parameters "are instantiated at runtime with numeric values". A monomorphizing compiler cannot do that for a computed size. There are two answers: restrict nat arguments to literals (bounded instantiation — refuses valid 1.0), or erase the nat to a runtime value (which undoes the type-level guarantee). Answer it on paper against `Library/ChunkedSparseArray.fss:48` (`object ChunkedSparseArray[\T, nat n\] extends Array1[\T,0,n\]`) and the Generator2 family (`Array2[\E,b0,s0,b1,s1\]`, four nat parameters) **before** any parser change.

**It is load-bearing for §2**, not a corner feature: `nat` is how the library declares its **array types**. Five census files block on it, the 80-file `array-and-matrix-types` bucket (65 under `--real`, `alone` 48) is downstream of the same thing, and `NatReflect` and `NativeArray` — both imported directly by `FortressLibrary.fss:13-14` — are in this set.

*Related scope-list hole to record in the same reconciliation:* decision 4's static-arguments item omits `opr`, while its "types that classify operator properties" item **requires** it — every trait in `Library/incomplete/advanced/Fortress.Operators.fsi.INCOMPLETE` takes one or more, and those ~30 declarations are `%`-commented LaTeX rather than Fortress source, so that decision-4 item starts from *writing* the declarations. (`Library/FortressLibrary.fss:2823` `trait Monoid[\T, opr OPLUS\]` is likewise inside a `(* ... *)` comment block, and `FortressLibrary.fsi:2023`'s `embiggen[\T,opr OP\]` is inside a comment too — there is **no live use of an `opr` static parameter anywhere in `Library/`**.)

#### D8. Distributions, regions and `at` — a v1 item with no acceptance criterion

Decision 4 names distributions as v1. `Distribution`, `blocked` and `subdivided` appear in **zero** of the 1956 corpus files. `Specification/advanced/parallelism-locality/distributions.tex:15` carries the spec's own note: "Distributions are not yet supported. Examples in this section are not tested." Every other item on every list in this document has corpus witnesses to differential-test against; this one has nothing.

Either cut it with a written deviation, or give it its own phase with an exit criterion that does not depend on an oracle that does not exist. Do not spike it while the cluster is shelved — a distribution with one node is untestable. The `at` **syntax** is separable and cheap by the spec's own licence: `regions-threads.tex:25` footnote says "the initial implementation of the Fortress language assumes a single machine with shared memory and exposes only the Global region", and `Library/FortressLibrary.fss:85-90` already ships `region()`/`here()` returning `Global`. 3 corpus files first-block on `at`.

#### D9. The oracle, and the licence

Two paperwork decisions that are cheap and currently blocking nothing except honesty.

- **Amend phases 0, 4 and 5**, or adopt the `.test` files as the oracle of record (§1, and the gate in §9). Whichever way it goes, the ROADMAP must stop naming an artifact that does not exist and a JVM path that was cancelled in a design document.
- **The licence contradicts itself.** `fortressc/Cargo.toml:16` declares `license = "Apache-2.0"` and every crate inherits it via `license.workspace = true`; `README.md` says "New code is unlicensed so far, pick something before the first release." The root `LICENSE` is the Sun/Oracle legacy text. A five-minute decision that is a hard blocker on any release.

### 3.2 Mechanism spikes whose result picks the branch

#### `SPIKE-EXCEPTIONS-MECHANISM` — the biggest owed decision in the backend

**Current state.** Zero unwinding machinery: no `invoke`, no `landingpad`, no personality function, no `resume`, and no `nounwind` attributes anywhere in `crates/codegen`. Every keyword in the family is refused at the parser (`throw`, `try`, `catch`, `finally`, `forbid`, `throws` on a non-`opr` declaration, `tryatomic`). There is no bottom type either, so `var a: ZZ32 = throw FooExn` has no typing. And the exception hierarchy does not exist as names: 2 corpus files get past the parser and die on `unknown type \`Exception\`` / `\`UncheckedException\``.

**Two measured runtime constraints already bound the choice.**
1. `fortress_abnormal_exit` is `_exit(1)` and **not** `exit(1)` *because* atomic-gate mutation 2 showed the `atexit` handler joins a pool whose worker is parked on a mutex the exiting thread holds. Any unwinding path must answer what happens to workers blocked in `fortress_parallel_for`'s done-wait when an exception crosses the join.
2. `atomic` is one **process-wide recursive** mutex. Unwinding out of an atomic region must release it, and atomic-gate mutation 4 (`NORMAL` instead of `RECURSIVE`) already produces a timeout on nested atomics, so the failure mode is measured.

**The spike is a mechanism spike, not a corpus-count spike.** Emit `invoke` around one call inside a parallel loop body and one inside an `atomic` region, and observe whether the pool join and the recursive mutex survive. That picks between LLVM invoke/landing-pads with a personality routine, a threaded error-return ABI, and `setjmp`/`longjmp` (which interacts badly with Boehm's stack scanning — decide that *in* the spike, not before). Only then is a file count meaningful.
*Branch:* if `invoke` survives, exceptions land as an ordinary codegen feature and the `throws`-clause type work follows. If it does not, either the runtime's join/lock discipline changes with it, or the error-return ABI wins and **every generated call signature changes** — which must be decided *before* the closure representation below, not after.

**The obligation that re-opens.** `atomic.tex:59-70`'s rollback-on-abrupt-completion is currently **unreachable, not violated**. It has two arms and they re-open at different times: the writes-**discarded** arm re-opens with exceptions, and the writes-**retained** arm re-opens with `label`/`exit`, which is the cheaper feature and will land first. At minimum, whichever lands must refuse a `throw`/`exit` crossing an `atomic` boundary with a named diagnostic, so the rule fails loudly instead of quietly.

#### `SPIKE-CLOSURE-REPRESENTATION` — one missing feature under five

**What sits on it.** The generator protocol (`Library/FortressLibrary.fsi:620`, `abstract generate[\R\](r: Reduction[\R\], body: E->R): R` — a higher-order signature), comprehensions, `BIG` operators over the `Reduction` trait, `spawn` (which `spawn.tex` desugars to `Thread[\Any\](fn()=>e)`), and every map/filter/fold in the library.

**Refused at three independent layers.** `fn` is a refused reserved word (1059 uses in 166 files — the most-used absent construct in the corpus). A bare function name in value position resolves to nothing (`unknown name \`g\``). And `Type` has **no arrow variant** and is deliberately `Copy` — M3e parsed arrow types and refused them precisely to keep it so, and `ast/src/nodes.rs:176-177` says the arrow type is "uninhabited", which is why refusing it today is correct rather than a gap.

**The branch.** (a) Fat pointer, code ptr + env ptr — requires `Type` to grow a boxed or interned composite variant and stop being `Copy`, touching every pass. (b) Lower a closure to a generated singleton-ish object with an `APPLY` method that enters the existing M3c whole-program dispatch — reuses machinery that works, but mints a tag per closure site and interacts with `MAX_INSTANTIATIONS = 4096` and the pre-`Checker::new` expansion fixpoint.
*How to run it:* implement (b) on the **smallest** case — a named function passed as an argument, no `fn` syntax at all — and observe whether the dispatch registry survives. That answers the representation question before any syntax work; (a) is only worth pricing if (b) fails.
*Runtime note:* a closure **stores a pointer**, so it must use `fortress_alloc_scanned`, never the atomic allocator. That distinction is measured, not assumed (`runtime/tests/array_trace.c`), and is the rule `02-stack` calls load-bearing.

#### `SPIKE-COMPOSITE-TYPE` — make `Type` non-`Copy`, or intern composites

**One decision under four decision-4 items.** Tuples (36 first-blockers of 1956 — 23 type + 13 expression); arrow types; dimensions (`dimensions.tex:22-45` makes `DimType` a production of `TypeRef`, composed by product, quotient and natural power — an abelian group of exponents a nine-variant `Copy` enum cannot hold); and the numeric tower (`RR32`, `NN32`/`NN64`, unbounded `ZZ`, bits and storage types — all `unknown type` today).

**It is the constraint, not a defect.** `types.rs`'s own doc comments say so: `Type` is `Copy` so it can be compared by value and stored inline everywhere, and `Elem` is a *separate* enum specifically so array-of-array is unrepresentable rather than merely rejected. Price it, do not treat it as a bug.

**Why urgent.** `overloading.tex:124-126` makes a functional's parameter a single value that **may be a tuple**, so tuples are load-bearing for the overloading chapter M3c already implements; and `conversions-coercions.tex:51-52` provides implicit coercions for tuple and arrow types, so **coercion cannot be finished before tuples are real**. Every month this waits, more passes are written against a `Copy` `Type`.
*Spike:* take the **interning** route on tuples only — trait and object names are already interned as `&'static str` — and measure the cost in `mono.rs` (which clones substitutions heavily) and in codegen. The 36 orders this; it does not price it.

#### `SPIKE-FIELD-MUTATION` — and it is one decision with accessors, not two items

**Why they are one.** `Specification/basic/expressions/bindings.tex:60-61`: "Assigning a left-hand field reference calls the corresponding setter method on the receiver object, passing the new value", and `:70-72`: compound assignment to a field "invokes the getter". So a direct GEP+store is a **named deviation to be decided**, not a mechanical port of the existing `Element` arm. Accessors are a live category (9 first-blockers of 1956), and a getter is today neither readable (`AccessorUnsupported`) nor callable (`DottedMethodUnsupported`) — two different error variants.

**What is already paid.** The blocker M3h named for accessors was dotted method dispatch, and **M3i landed it** — `O.m(1)` and trait-receiver dispatch both work. The exclusion is a `continue` on `m.accessor` at five sites (`types/src/lib.rs:580, 602, 695, 874, 1098`, `mono.rs:152, 661`) inside an otherwise-working member walk. The object layout already has the storage (one scanned block, 32-bit tag at 0, fields at +8) and Boehm needs no write barrier.

**Correct the blast radius before sizing it.** The claim that `List`/`Map`/`Heap`/`Avl` mutate fields is **false**: there is not one dotted field assignment anywhere in `Library/` or `CompilerLibrary/`, and every `:=` in those four files is a local or a declaration. The real stdlib users of mutable fields are `Random.fss`, `Format.fss` and `PrefixSet.fss`.

**What it unlocks and what it breaks.** Unlocks mutable data structures, `o.f := v`, setters, tuple assignment targets, and the field sites of `||=`. **Breaks the M5 shared-array soundness argument** — `04-state`'s own reasoning is "`f(h)` where `h` is an object holding an array would pass; no field store exists in the language yet, so nothing can exploit it today." Schedule the whole-program reachability pass **in the same change** and re-run `tools/parallel-gate.sh --mutate` with `badsharedarray.fss` confirmed still refused, plus `memory-gate.sh` and `runtime/tests/array_trace.c`.

*Note on the parser half:* the `=` spelling of a mutable field **parses** and is refused by a tested checker diagnostic (`` `var x`: mutable fields are not implemented ``, `types/src/lib.rs:522`, asserted at `crates/types/tests/types.rs:821`). Only the `x: T := e` and `var x: T := e` spellings — which is what the corpus writes, e.g. `ProjectFortress/tests/atomic5.fss:16` — die in the parser. So the AST and diagnostic slot exist; the work is the checker, the `Slot::Field` lowering and `assign`.

**The structural fact.** Exactly one generator form works: `i <- lo#hi`, `i <- lo:hi`, plus `seq(...)`. ### 6.2 Runtime faults, in a project whose stated rule is that failures halt with a diagnostic

- **Integer division by zero faults.** `d(a,b) = a/b` then `d(7,0)`: compiles at exit 0, binary dies `Floating point exception (core dumped)`, rc 136, on a bare `sdiv` with no guard. `02-stack` says a subscript "halts with a diagnostic and exit 1 rather than faulting"; `shims.c:642-645` says of the dead dispatch arm that "'unreachable' should mean a clean halt with a diagnostic rather than undefined behaviour." **Division got neither.** `DivideByZero` is named across four spec files. RR64 division is correct (`1.0/0.0` → `inf`).
- **Three of the 291 binaries die with SIGSEGV** (§1, phase 5): unbounded mutual recursion through overridden methods, no stack guard, so a signal with no diagnostic.
- **Nothing in `tools/` gates arithmetic at all** — no `sdiv`, no division-by-zero, no overflow case. By this project's own standard ("a gate is not trusted until it has refused"), the arithmetic lowering has never been asked to refuse anything.
- *Observed, not adjudicated:* `ZZ32` overflow wraps silently (`2147483647 + 1` → `-2147483648`). The spec position on wrapping is not pinned by anything found on disk, so whether that is a deviation is itself an open question.

### 6.3 Diagnostics that name the wrong mechanism

This is the class the sibling kernel project recorded as costing an hour, and it **corrupts the triage map the whole plan is steered by**: files land in the wrong bucket, so their feature is undercounted and `missing-library` (140 of 1956, 115 of 1588) is inflated by an unknown amount.

`f(x = 3)` → `unknown name x` (keyword arguments, a decision-4 v1 feature, has **no bucket of its own**). `x instanceof T` → `unknown name instanceof`. `FF_16` → `unknown name FF_16`. `return 1` → `unknown name \`return\``. **Any** unknown name carrying static arguments → `` `X` takes no static arguments `` rather than `unknown name` — and since the legacy library is written almost entirely in generic call syntax, this misreports the cause for a large share of the library axis specifically. `[a b] = m` → `unknown name \`a\``, so nothing names matrix unpasting. A `where` clause on a continuation line → `expected a field or method name, found KwWhere`, and a where clause is not a member. `Library/GeneratorLibrary.fss` reports `expected \`)\`, found KwSelf` at a byte that reads as a parameter-list failure and is actually column 52, the `self` inside `NOT (elt IN self)`.

### 6.4 Correctness holes with a two-line reproducer

- **The `where`-clause bound is a silent no-op** (§5.2). Confirmed on objects *and* functions. Fix: route the trait-constraint form into the existing `BoundObligation` / `discharge_bounds` path; refuse the other five where-clause forms by name; negative fixtures for both call sites. **Expect losses in both directions** — text that compiles today will start refusing. Do not do it before the where-clause-variable decision (§4.4).
- **The `widen` advice is a dead end — for RR64 targets only.** `widen` is hardcoded ZZ32→ZZ64 (`types/src/lib.rs:3459-3481`, one construction site for `Target::Widen` in the whole workspace), while `is_widening_of` recognises **three** widenings and drives the advice. So `y: ZZ32 = 3; x: ZZ64 = y` → the advice **works**; `y: ZZ64 = 3; x: RR64 = y` and `x: RR64 = widen(3)` both fail with the advice repeated one type up, and `widen(widen(x))` fails at the inner argument. **There is no expressible way to get an RR64 from a ZZ32 anywhere in the language.** Fix: read the target from `expected` and the source from the argument, accept any pair `is_widening_of` recognises, and add int-to-float in the shim. State the mutation before claiming green.
- **`ProjectFortress/tests/XXXimmutable0.fss`** compiles and prints `x = 0`. 1.0 forbids an immutable binding shadowing a mutable one; the compiler does not implement it and never did — M5's block-level `var` **exposed** the gap rather than creating it. `COMPILE_FLOOR` is 290 for this. **And there is a second shadowing rule recorded nowhere**: a static parameter may not shadow an enclosing type name, tested by `XXXtypeParamShadowing`, which runs and prints its own failure banner. Decide both together; they are separate edits (the first is the checker's Binding path, the second is the expansion pass, which freezes before `Checker::new`).
- **Trait/object clause order is unenforced**, and that laxity was introduced *deliberately* ("costs nothing and removes a second way to be wrong"). But 1.0 requires `extends` first, `XXXtraitClauses.fss` exists to test it, and the M6 problem that motivated the loop was the **continuation line**, which is orthogonal to ordering. Member declaration order is likewise unenforced (two more must-fail tests).

## 7. Settled decisions a reader would otherwise mistake for gaps

Each of these looks like a hole and is a decision. Cited, not re-litigated.

**Scope decisions.**
- **Syntax abstraction is cut** (ROADMAP decision 1, measured): 34 files declare a `grammar`, all under `syntax_abstraction_tests/`, `Library/` has **zero**, and the three `Library/` files touching the macro APIs are 218 lines nothing else imports. Consequence: conformance is quoted against **1846**, and the 11 `SXX` must-fail files are outside the negative gate. Triage still shows 23 syntax-abstraction first-blockers because triage does not apply decision 1 — do not read those as a gap. **v1 is a Fortress dialect, not the whole language**, and the README already says so.
- **The ASCII core grammar is permanent** (decision 3, `02-stack`). Every construct has an ASCII spelling that always works; Unicode spellings are a curated allowlist plus library aliases, explicitly **not** Sun's `ID_Start`/`ID_Continue` dump. The 6 census files blocked on non-ASCII are blocked on the allowlist not existing (§2.4), not on the decision.
- **Slurm, sbatch, multi-node, InfiniBand and AVX-512 cluster tuning are shelved, not cancelled** (`02-stack` posture 2026-08-18; ROADMAP:16-19). Phase 7's exit says "on one node", so the shelving does not touch it.
- **Eclipse, Emacs, Fortify rendering, Vim, `contrib/`** — ROADMAP's out-of-scope list, verbatim.

**Design decisions inside the compiler.**
- **Ambiguous dispatch is a compile error** naming the tuple and both declarations, where 1.0 picks an arbitrary winner; and **exclusion is closed-world**. Two signed-off M3c deviations. *But note the boundary:* that covers the relation M3c **computes**; it does not license accepting a program whose own `excludes` clause it contradicts (§5.2).
- **Monomorphization, never erasure and never boxing**, `MAX_INSTANTIATIONS = 4096` per component, **polymorphic recursion refused** (`PureList.fss:137` is real and no monomorphizing compiler compiles it at any limit). Do not re-open the strategy as a way of closing a gap — anything cheaper under erasure (nat parameters especially) must be solved *within* monomorphization or be a named deviation.
- **Static arguments are written, never inferred** — what makes demand syntactic and lets expansion run before `Checker::new`. `X is generic; write its static arguments` is a designed diagnostic.
- **The static-parameter uniformity rule is enforced and permanent**, and `overloading.tex:100-105` agrees verbatim. The 22 files refused on it are a correct refusal. *What is not settled:* the check is coarser than alpha-equivalence and skips methods, and `Library/QuickSort.fsi` violates the rule (§1, §4.4).
- **`Type` is `Copy` and `Elem` is a separate enum** so array-of-array is unrepresentable rather than merely rejected. Cite it as the constraint §3.2 must price, not as a defect.
- **"A value is never implicitly converted"** is the deliberate posture stated at the top of the checker. Keep it separate from the coercion gap: 1.0's `coerce` facility is absent (a gap), but no-implicit-widening is the design.
- **Arrays refuse a reference element type** — a deliberate allowlist whose reason is measured, with a stated re-entry door (`fortress_array_alloc`).
- **Two allocators**, atomic for pointer-free bytes and scanned for anything holding a pointer, and the distinction is measured in `runtime/tests/array_trace.c`.
- **Only a `:=` binding gets an `alloca`, and every `alloca` is in the entry block** — otherwise a mutable declared inside a loop body is a silent stack overflow.

**M5-era decisions.**
- **Reduction variables go beyond 1.0** — five spec chapters say "not yet supported"; M5 implements them anyway as a named M3c-style deviation. The lock is **elided** for a block writing only reduction variables, licensed by `reduction.tex:40-42`.
- **RR64 reductions are deterministic per worker count and not across** — inherent to reassociation, permitted by `reduction.tex:43-46`; the gate pins `FORTRESS_WORKERS` rather than asserting a false equality. ZZ32/ZZ64 **are** exact at every count.
- **The merge is emitted in the caller**, not the shim, because it is typed and the shim has no type knowledge; it still satisfies "at the join barrier".
- **Accumulators are atomic (unscanned) memory**, safe only because the checker restricts reduction variables to ZZ32/ZZ64/RR64.
- **The shared-array refusal is bare-`Var`-arguments-only**, the cheap fix the design named, with the reachability pass as the right answer — and it is sound **only** while no field store exists (§3.2).
- **`*=` and `/=` were measured at zero corpus uses and deliberately not added**; `/=` sits next to `=/=`. `CompoundOperatorUnsupported` is unreachable through today's parser on purpose.
- **`io` inside `atomic` compiles and is serialised** — a **named** deviation (we have no `io` modifier). And `atomic`/`io` were deliberately kept **out** of the modifier set so they stay loud rather than silent.
- **Atomic rollback on abrupt completion is unreachable, not violated** — and it re-opens in two stages (§3.2).
- **The nested-loop environment allocation** is M4's shape, expensive not incorrect, explicitly deferred.

**Lexical decisions.**
- `1e10` is refused **correctly** (no exponent syntax in Fortress; exponents are written `10^25`). `3.asString` likewise. Word pasting is skipped matching the reference. Lexer fail-fast is a recorded improvement over the reference's phantom duplicates — **it covers the lexer only**, not the parser or checker (§4.6).
- **`^` is left-associative and `2^3^2 = 64` is correct.** `XXXTwoThreeTwo` must fail for another reason; do not "fix" this.

**Instrument decisions.**
- **`comprises { ... }`'s open-set marker is dropped** — honest only while nothing reads `comprises`, and `comprises.tex` makes `...` legal only in an api, so it must close together with §2.6.
- **Declaration modifiers are recorded and not read**, and `abstract` should stay derived from `body.is_none()`. *The gap is the acceptance of illegal programs* (§5.2), not the unread flag.
- **Must-fail negative tests stay refused by name**, and gate floors sit one below the count for exactly that reason.

## 8. Out of scope for "compiler 100%"

- **Phase 6's remainder.** The C-ABI half is done and gated; what remains is the literal two-node rank count, and there is no cluster. Also absent and staying absent for now: every point-to-point and collective MPI operation. When it un-shelves, the spike is a two-rank send/recv through a shim pair, to find out whether MPI datatypes can stay entirely inside `mpi_shims.c` the way `MPI_COMM_WORLD` does.
- **All of phase 8** — Apptainer batch scripts, Slurm, four nodes, AVX-512 tuning. Note the one piece of phase 8 that *is* a language-side blocker and belongs in §4.6 rather than here: the array-slot call is a vectorisation barrier at any optimisation level.
- **Syntax abstraction**, cut by decision 1 (§7).
- **Arbitrary Unicode identifiers**, out by decision 3.
- **A general C-ABI declaration form for user code** is *not* shelved by decision and is owned by no phase — flag it to whoever writes D5, because it is the same boundary question.
- **The legacy interpreter as anything but a differential oracle**, and it is scheduled for deletion once phase 7 passes.

**The consequence of that last one that nobody has drawn.** `grep -rn 'not yet supported' Specification --include=*.tex` returns **51 occurrences across 49 of the 172 files**, 45 of them in `basic/` or `advanced/`, sitting at the head of the chapter as an editorial note naming what Sun never finished. **At least ten of decision 4's sixteen v1 features carry one**: dimensions and units, non-type static parameters, static expressions, keyword and varargs parameters, coercion and where clauses, tests and properties, matrix unpasting, multifix, distributions — plus type aliases, method contracts and the `atomic`/`io` functional modifiers. For those chapters there is **nothing to diff against**: they are spec-reading work, not porting work, and phase 4's exit criterion ("disagreements with the legacy interpreter documented") does not apply to them. That belongs in D6.

Ordered by what unblocks measurement, what gets more expensive with time, and what makes the metric mean what people think it means. Not by first-blocker count.
