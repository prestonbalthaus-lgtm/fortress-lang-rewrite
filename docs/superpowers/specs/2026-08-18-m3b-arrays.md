# Fortress M3b: arrays and iteration

Date: 2026-08-18
Status: implemented, gated

The first data structure, and the first loop. Both are deliberately primitive:
traits and generators are M3c, and building either of them into arrays now
would mean building them twice.

## What the language gained

```
component arraysum
export Executable

run() = do
   n:ZZ64 = 100
   squares:Array[\ZZ64\] = array(n)

   i:ZZ64 := 0
   while i < n do
      squares[i] := i i
      i := i + 1
   end
   ...
```

* `Array[\T\]`, one dimensional and homogeneous, holding any scalar.
* `[1, 2, 3]` literals, `array(n)` for a sized one, `a[i]` to subscript,
  `length(a)` for the length.
* `x:T := e` declares a mutable, `x := e` assigns, `a[i] := e` writes an
  element.
* `while cond do ... end`.

`|a|` is the Fortress spelling of length and is not here. It needs `|` to be an
operator, and an operator that is its own closing bracket is ambiguous with
juxtaposition in ways that only a real precedence layer settles. `length` is a
name, and a name costs nothing to alias later.

## Decisions that shaped the rest

**Subscripts are ZZ64.** Not ZZ32, and not "whatever integer you have". The JVM
implementation's hard ceiling was array indexing at 2^31, and it is the reason
this project exists; a ZZ32 index would rebuild that ceiling in the first data
structure. The no-implicit-conversion rule applies here like everywhere else, so
a ZZ32 variable in a subscript is `ImplicitWideningRejected` and the fix is
`widen`. There is a test for it, because a new boundary is exactly where a rule
quietly stops holding.

**`x := e` assigns and never declares.** `x:T := e` declares. Allowing a bare
`i := 0` to declare when `i` is unbound and assign when it is bound means a typo
inside a loop body silently shadows the counter instead of failing. The
diagnostic names the fix: ``i` is not declared; write `i:T := ...``.

**The binding is immutable, the container is not.** `a:Array[\ZZ64\] = array(n)`
cannot be rebound, and `a[0] := 7` is still legal. Those are different
properties and conflating them would make every array binding mutable for no
reason.

**Only a mutable binding gets storage.** Immutable bindings stay SSA values, so
the generated code for everything written before M3b is unchanged, down to the
`phi` in the factorial.

**Nesting is unrepresentable, not rejected.** `Type::Array(Elem)` where `Elem`
is a separate five-variant enum. `Array[\Array[\ZZ64\]\]` fails in
`resolve_type` with a specific diagnostic, and no later pass has to consider a
case the type system cannot express.

## The array, in memory

One allocation. The header and the elements are a single block, so an array is
one object to the collector and a slot is a fixed offset from its base:

```c
typedef struct {
    long long length;
    long long elem_bytes;
    char data[];
} FortressArray;
```

`elem_bytes` lives in the header rather than being passed at every access,
because a width that codegen and the runtime both carry is a width they can
disagree about.

**Allocated scannable, with `GC_malloc`.** This is the landmine M3a wrote into
`shims.c` and it is now the thing M3b's gate measures. String allocation uses
`GC_malloc_atomic`, which is memory the collector does not trace: right for
bytes, and fatal for an `Array[\String\]`, whose elements are real pointers and
whose contents would be reclaimed while the array still pointed at them.

Storage is filled explicitly rather than relying on the allocator zeroing it:
the memory gate's negative control is plain `malloc`, which does not zero, and a
pointer slot has to start as a valid empty string rather than a null.

Three C entry points: `fortress_array_alloc`, `fortress_array_length`, and
`fortress_array_slot`, which bounds checks an index and returns the address.
Every read and every write goes through the last one, so there is exactly one
place the check can be missing from. The load or store through that address
stays typed in IR.

`Boolean` is a byte in an array and an `i1` in a register, so the two cross
through a `zext` and a `trunc`.

## Out of bounds halts, and says why

```
$ ./oob
fortress: array index out of bounds (5, 3)
$ echo $?
1
```

A diagnostic and a status, not a signal. The gate refuses status 139 and 134
specifically, because a segmentation fault and an abort are what a missing check
looks like.

## The trap that would have shipped

`alloca` belongs in the entry block, not where the declaration appears. A
mutable declared inside a loop body is one stack slot for the function, not one
per iteration; emitted at the insert point it is the latter, and at any real
iteration count that is a stack overflow with no diagnostic at all.

`tests/loopalloca.fss` runs a million iterations declaring four mutables each.
It passes, and with the `alloca` moved back to the insert point it dies with
SIGSEGV, status 139. That is the whole of the evidence and it took one mutation
to get.

## The gate

`tools/array-gate.sh`, 14 checks, six of them the self test.

**The sum is computed, not copied.** The gate evaluates `n(n-1)(2n-1)/6`
itself and compares. A gate that reads the answer out of the program's output is
only checking that the program agrees with itself. The self test pins the closed
form against two known values, 328350 for 100 and 285 for 10.

**The clean-halt assertion is self tested in both directions**: it accepts
status 1 and refuses 139, 134 and 0.

**Tracing is measured, not hoped for.** Reading an array back after a collection
is not a test: freed memory usually still reads correctly, and it does here. The
first attempt at this proof was a Fortress program that filled an array with
heap strings, allocated a million garbage strings to force collections, and read
the array back. It passed identically with the array allocated atomically, which
means it was proving nothing.

`runtime/tests/array_trace.c` measures the thing itself. It fills an array with
8 MB of heap-built strings in a function whose frame is then gone, forces two
collections, and reads live bytes from the collector:

```
scannable : payload 8,388,608   live 12,595,200
atomic    : payload 8,388,608   live 36,864      -> refused
```

Eight megabytes reclaimed while the array was still holding it. That is the
difference between a landmine documented and a landmine disarmed.

**All three mutations were run and each is caught by exactly one check:**

| mutation | check that refused | evidence |
|---|---|---|
| array storage `GC_malloc_atomic` | the collector sees the elements | 36,864 live of 8,388,608 |
| bounds check deleted from the slot shim | out of bounds halts cleanly | status 0, no diagnostic, read past the end |
| `alloca` at the insert point | a mutable in a loop body | status 139 |

The second one is worth its own sentence. Without the check the program did not
crash: it read past the end of the array and exited 0. Silently wrong is what
the check prevents, and the gate saw it.

## Corpus

Adding `[` and `]` moved the lexer from 597 files to **939 of 1956 (48.0%)**.
Brackets are everywhere in the legacy tree and nothing could lex past them.

The parser is unchanged at 52. What blocks it is `trait` (147), `object` (107)
and `api`, which is M3c and beyond, not arrays.

## What M3b does not do

No `for`, no generators, no comprehensions, no reductions. `for` in Fortress is
parallel by default and cannot be honestly faked with a counter, so it waits for
the machinery that makes it real.

No nested arrays, no slices, no bounds-check elimination, no resize. `while` is
the only loop.
